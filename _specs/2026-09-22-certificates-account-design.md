# Design: сертификаты в личном кабинете и автооткрытие выдачи

**Узел:** `К-12` · **Родитель:** `К-11` (`_specs/2026-09-22-congress-certificates-design.md`) → `Л-01` · **Реестр:** `_specs/PLAN.md` · **Дата:** 2026-09-22
**Одобрено:** Alex, 2026-09-22: «Нужно добить уже сертификаты… по прохождению конференции в своём аккаунте каждый мог забрать свой сертификат». Выбор в вопросах: «Кабинет + страница», «Всем зарегистрированным», «Сама после окончания».

## 1. Задача

К-11 выдаёт сертификат без входа: человек ищет себя по Ф.И.О. и подтверждает телефоном, выдачу открывают вручную. Теперь нужно:

1. **Получатели — все зарегистрированные.** Список берётся из `congress_registrations` одной кнопкой в админке. Выгрузка «Экспорт CSV» тоже годится для импорта (у неё и так колонки `Фамилия/Имя/Отчество/Телефон`, теперь ещё и `Email`).
2. **Личный кабинет** `/profile`: ссылка в шапке уже есть, маршрута не было. После входа участник видит свои сертификаты и скачивает их без телефона.
3. **Выдача открывается сама** на следующий день после окончания конгресса (по Ташкенту), если бланк загружен. Админ может открыть раньше или закрыть.

Страница поиска К-11 (`/congress/:id/certificate`) остаётся для тех, у кого нет учётной записи.

## 2. Привязка к учётной записи — по email

Регистрация на конгресс идёт без входа, `congress_registrations.user_id` никогда не заполняется. Единственная связь человека с его регистрацией — email. У получателя сертификата появляется поле `email`, в кабинете показываются получатели, у которых `email` совпадает с `users.email` (без учёта регистра и пробелов по краям).

**Известный риск, принят:** email учётной записи не подтверждается. Кто заведёт учётную запись на чужой email, скачает чужой сертификат (с чужим именем). Это того же порядка, что поиск по имени у участника без телефона в К-11; лимит 5 выдач общий для кабинета и страницы поиска.

**Регистр почты** (решение Alex 2026-09-24, по находке ревью). Вход искал пользователя по строке как есть, а получателей К-12 сопоставляет по `lower(email)`: человек, заведший учётную запись как `Sitora@Mail.UZ`, не вошёл бы, набрав `sitora@mail.uz`, и до кабинета бы не дошёл. Поэтому в этот же узел входит починка auth: почта сохраняется нормализованной, поиск пользователя при входе и в `get_current_user` — регистронезависимый, уже существующие в базе дубли по регистру разрешаются детерминированно. Заодно `get_current_user` начинает проверять `is_active` — кабинет первым открывает персональные данные по токену обычного пользователя.

## 3. Данные — миграция `006`

- `certificate_recipients.email` — `String(255)`, nullable, индекс. Хранится уже нормализованным: `strip().lower()`; пусто или без `@` → NULL.
- `certificate_templates.issue_mode` — `String(10)`, NOT NULL, по умолчанию `'auto'`, CHECK `in ('auto','open','closed')`. Заменяет `is_open`: апгрейд переносит `is_open = true → 'open'`, иначе `'auto'`, затем удаляет `is_open`. Даунгрейд: `'open' → true`, остальное → false.

## 4. Когда выдача открыта

Функция `certificates_open(mode, has_pdf, date_end, today)` — чистая, покрывается unit-тестами:

- нет бланка → закрыто;
- `open` → открыто; `closed` → закрыто;
- `auto` → открыто, если `date_end` задана и `today > date_end` (даты в `Asia/Tashkent`). `date_end` пуста → закрыто.

`today` — дата в `Asia/Tashkent`, берётся функцией `_today()`, которую тесты подменяют. `opens_on` = `date_end + 1 день` (для `auto` с бланком и заданной датой, пока закрыто), иначе `null`.

`GET /congresses/{id}/certificates/status` → `{"open": bool, "opens_on": "YYYY-MM-DD" | null}`. Подсказки, выдача и кабинет используют одно и то же правило.

## 5. API

**Кабинет** (`Depends(get_current_user)`, в `api/certificates.py`):

| Метод | Путь | Поведение |
|---|---|---|
| GET | `/api/congress/my-certificates` | Получатели с `email = lower(user.email)` по всем конгрессам: `[{recipient_id, congress_id, congress_title_ru, congress_title_uz, congress_title_en, full_name, number, downloads_left, open, opens_on}]`, свежие конгрессы сверху. Телефонов в ответе нет |
| POST | `/api/congress/my-certificates/{recipient_id}/download` | Получатель не найден или email не совпал → 404 `not_found`; выдача закрыта → 404 `not_found`; лимит → 403 `limit_reached`; иначе PDF, как у `issue`. Частота — то же ведро `issue` (20/мин на IP) |

Списание и сборка PDF выносятся из `issue_certificate` в общий помощник: оба пути делают одно и то же условное `UPDATE … download_count < 5 RETURNING`, откат при сбое сборки.

**Админка:**

- `certificate-settings`: `is_open` → `issue_mode`; в ответе ещё `open` и `opens_on` (посчитанные, только для чтения).
- `POST /congresses/{id}/certificate-recipients/import-registrations`, form `mode=append|replace`, `dry_run` — то же, что CSV-импорт, но строки берутся из `congress_registrations` этого конгресса: `full_name = "Фамилия Имя Отчество"`, телефон через `clean_phone`, email. Отчёт того же вида (`columns` = `[]`). Логика дублей, нумерации и `replace` — общая с CSV-импортом (выносится в помощник).
- `parse_recipients_csv` дополнительно распознаёт колонку email: `email`, `e-mail`, `почта`, `эл. почта`, `электронная почта`.
- Получатель (ответ, создание, правка) получает поле `email`; невалидный (непустой без `@`) → 422 `invalid_email`.

## 6. Фронтенд

- `pages/Profile.jsx`, маршрут `/profile` (ленивый кусок, как остальные публичные). Без входа → `/login`. Показывает Ф.И.О. и email учётной записи и блок «Мои сертификаты»: название конгресса на языке интерфейса (фолбэк RU), Ф.И.О. на сертификате, номер `No. 001`, «осталось N из 5», кнопка «Скачать сертификат» (открыто), «Будет доступен с ДД.ММ.ГГГГ» (есть `opens_on`), «Выдача пока не открыта» (иначе). Пусто → «Сертификаты привязаны к email, указанному при регистрации на конгресс. Если вы регистрировались с другим email, найдите себя по Ф.И.О. на странице конгресса».
- `CongressCertificate.jsx`: при закрытой выдаче с `opens_on` — «Выдача откроется ДД.ММ.ГГГГ»; подсказка «Есть учётная запись? Сертификат доступен в личном кабинете» со ссылкой на `/profile`.
- Ссылка «Получить сертификат» на странице конгресса — как в К-11, по `status.open`.
- Админка, вкладка «Сертификаты»: вместо галочки «Выдача открыта» выбор «Автоматически после окончания конгресса / Открыта сейчас / Закрыта» и строка текущего состояния («Сейчас закрыта, откроется ДД.ММ.ГГГГ»). Кнопка «Взять из регистраций» рядом с импортом CSV, с тем же порядком: сначала сводка `dry_run`, замена через `ConfirmDialog`. В таблице получателей колонка «Email», в форме получателя поле «Email».
- `services/api.js`: `contentAPI.getMyCertificates`, `contentAPI.downloadMyCertificate` (blob, ошибка — разбор JSON из блоба, как у `issue`), `contentAPI.importCertificateRecipientsFromRegistrations`. Импорт — в `contentAPI`, а не в `adminAPI`: там же лежат остальные админские методы сертификатов, потому что `adminAPI` обслуживает только пути `/admin/...`.
- i18n: ключи `profile.*` и новые `certificate.*` во всех трёх `locales/{ru,uz,en}.json`.

## 8. Выкатка в два шага (решение Alex 2026-09-24)

`006` — первая миграция репозитория, меняющая живую таблицу: `create_all` в `main.py` прикрывал только создание таблиц целиком. При прежнем порядке выкатки (`up -d --build backend`, затем `alembic upgrade head`) новый контейнер несколько десятков секунд читал бы ещё не созданный `issue_mode` → 500 на `/certificates/status`, который дёргает публичная страница конгресса.

Поэтому «расширить, потом сузить»:

1. **Этот узел.** `006` добавляет `issue_mode` и переносит в него `is_open`, но **колонку `is_open` не удаляет** — работающий старый контейнер переживает применение миграции. `deploy.yml` собирает образ, прогоняет миграцию разовым контейнером нового образа и только затем поднимает backend. Окна с ошибками нет ни у старого кода (его колонка на месте), ни у нового (схема уже новая).
2. **Следующая выкатка.** Миграция `007` удаляет `is_open`. Отдельным узлом, после того как выкатка `006` подтверждена на проде.

Модель `certificate_templates` про `is_open` не знает уже сейчас: лишняя колонка в БД новому коду не мешает, а на свежей установке `create_all` её просто не создаёт.
